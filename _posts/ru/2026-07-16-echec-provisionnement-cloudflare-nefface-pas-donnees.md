# Worker может завершиться с ошибкой, не заставляя исчезнуть всё остальное

20 мая я добавил автоматический провижининг Cloudflare Worker при создании нового элемента в моём приложении. Идея была практичной: одно действие в дашборде создавало данные, подготавливало их коллекцию и развёртывало Worker, который будет их использовать.

Проблема обнаружилась в обработке ошибок. Если развёртывание Cloudflare падало после создания данных, API удалял элемент и, если коллекция тоже только что появилась, саму коллекцию. Ошибка инфраструктуры обрабатывалась так, словно бизнес-запроса вообще не было.

> Одной фразой: 28 мая я заменил откат, удалявший бизнес-данные, на успешный ответ с предупреждением и явной попыткой очистить частично созданный Worker.
{: .prompt-info }

## Отправная точка: одно действие, несколько систем

Создание из дашборда запускало цепочку операций с разными гарантиями: база приложения, коллекция данных и API Cloudflare. SQL-транзакции через эту границу не существовало: каждый шаг мог пройти успешно, а следующий — завершиться ошибкой.

| Зона | Поведение до исправления |
|---|---|
| Бизнес-элемент | Удалялся при сбое автоматического развёртывания Worker |
| Коллекция, созданная во время запроса | Тоже удалялась |
| Частично созданный Worker | Отдельной очистки в этом пути не было |
| Ответ API | Ошибка: казалось, что создание полностью провалилось |

На бумаге такое поведение выглядело аккуратно: «если развёрнуто не всё, откатываем всё». На деле оно смешивало два уровня ответственности. Создание данных долговечно и воспроизводимо; развёртывание Worker зависит от внешней системы, которая может дать сбой из-за временной проблемы или конфигурации.

Поэтому худшим сценарием был не просто отсутствующий Worker. Пользователь только что создал данные, а backend удалял их вместо него, чтобы скрыть сбой внешнего вызова.

## Правило: компенсировать только то, что относится к развёртыванию

Я установил простое правило: ошибка провижининга не должна отменять уже валидное бизнес-создание. Но если внешний вызов оставил после себя Worker, API должен попытаться удалить его и точно объяснить клиенту результат.

>Правила, не подлежащие обсуждению:
>1. **Не удалять элемент и его коллекцию** после сбоя внешнего развёртывания.
>2. **Очищать только потенциально осиротевший ресурс Cloudflare**.
>3. **Возвращать успешный ответ с предупреждением**: клиент должен знать, что данные существуют, но Worker требует вмешательства.
{: .prompt-danger }

Это не волшебная распределённая транзакция. Это точечная компенсация: я не делаю вид, что могу вернуть несколько сервисов в атомарное состояние, а явно ограничиваю очистку ресурсом, который мог быть создан последним побочным эффектом.

## Исправление: сохранить данные, зафиксировать компенсацию

Коммит от **28 мая 2026 года** меняет один backend-файл: **49 добавлений** и **18 удалений**. Блок отката, стиравший элемент и коллекцию, заменён состоянием очистки Worker.

```js
const cleanupState = {
  attempted: false,
  deleted: false,
  skipped: false,
  error: null
};

// Единственный побочный эффект, который нужно компенсировать, — внешний Worker.
await cloudflareApiRequest({
  method: 'DELETE',
  path: `/accounts/${accountId}/workers/scripts/${workerId}`,
  token,
  timeout: 45000
});
cleanupState.deleted = true;
```

У компенсации есть важная тонкость: ответ `404` на `DELETE` считается успешной очисткой. Здесь цель не в том, чтобы доказать, что Worker существовал, а в том, чтобы гарантировать его отсутствие после обработки.

Итоговый ответ различает три понятных случая: очистка выполнена, пропущена из-за отсутствия необходимого контекста либо запущена, но завершилась ошибкой. API сохраняет эту информацию в отдельном поле предупреждения, а не прячет в общей ошибке.

| Ситуация после сбоя Cloudflare | Ответ дашборду |
|---|---|
| Worker удалён, в том числе если API вернул `404` | Создание успешно, предупреждение о выполненной очистке |
| Недостаточно идентификаторов или конфигурации | Создание успешно, предупреждение о пропущенной очистке |
| Удаление в Cloudflare завершилось ошибкой | Создание успешно, предупреждение о неудачной очистке |

Frontend теперь может показать понятное действие: созданные данные пригодны к использованию, а развёртывание нужно повторить или проверить. Главное, временная ошибка провайдера больше не превращает успешное создание в бесследное исчезновение.

## Честная часть: первый откат был слишком агрессивным

Виноват был мой первоначальный короткий путь. Я считал «автоматический провижининг» неделимой операцией и выбрал полный откат, чтобы избежать неполных состояний. Это успокаивало, но было неверно: коллекция и элемент приложения — не то же самое, что удалённый Worker.

Новый код тоже не обещает полного отсутствия промежуточных состояний. Если очистка Worker не сработает, может остаться ресурс, который придётся обработать. Разница в том, что теперь это состояние **явно сообщается**, сохраняется на бизнес-стороне и потому восстанавливается без просьбы к пользователю заново создавать свои данные.

Ещё одно намеренное ограничение: в это исправление я не добавлял отложенное автоматическое удаление или фоновый retry. Коммит сосредоточен на ответе на запрос: ничего не уничтожать по ошибке, сразу попытаться выполнить компенсацию, затем сообщить результат.

## Итоги: компенсация честнее фиктивного отката

| Проверяемая метрика | Результат |
|---|---|
| Изменённый файл | `gXd.node/config-api.js` |
| Diff исправления | **49 добавлений, 18 удалений** |
| Бизнес-данные, удалённые после сбоя развёртывания | **0** после исправления |
| Отображаемые состояния очистки | удалено, пропущено или ошибка |
| Дата исправления | 28 мая 2026 года |

В процессах, вызывающих несколько сервисов, правильный вопрос не «как отменить всё?», а **какой шаг действительно безопасно отменить и какое состояние должно оставаться видимым, если это невозможно?**

Здесь сохранить данные и сделать сбой Worker наблюдаемым надёжнее, чем притворяться, будто вся операция была транзакционной. Самый безопасный откат не всегда удаляет больше всего: он уничтожает только тот побочный эффект, за который отвечает.
