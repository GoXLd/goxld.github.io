# Семь исправлений OVHcloud: сначала доказать, затем предложить

Всем привет!

В конце июля я поставил себе простую цель: внести вклад в публичную документацию OVHcloud, не создавая искусственную работу ради заполнения профиля GitHub. Никакой ежедневной нормы pull request'ов, никаких косметических правок, представленных как крупные инциденты. Я хотел найти технические дефекты, которые мог доказать официальными источниками, исправить в пределах своей компетенции и проверить до обращения к maintainers.

Первый цикл завершён: **приняты семь наборов исправлений**, четыре напрямую из моих pull request'ов и три после переноса во внутренние ветки репозитория. Они охватывают **55 файлов** и семь языков, а изменения затрагивают доступность React, Apache, Docker Compose, OpenStack и Node.js.

> Одной фразой: семь принятых вкладов, 55 исправленных файлов, четыре прямых merge и три внутренних переноса — при одном неизменном правиле: воспроизводимое доказательство перед каждым изменением.

## Отправная точка

Репозиторий `ovh/ovhcloud-docs` — не просто набор Markdown-страниц. В нём находятся опубликованные на нескольких языках руководства, React-тема сайта, скрипты генерации и проверки содержимого. Поэтому на вид крошечное исправление может затронуть семь языковых вариантов или изменить поведение клавиатуры в нескольких layouts.

| Зона | Состояние до исправления |
|---|---|
| Фильтры поиска | визуальная группировка без нативного семантического HTML-элемента |
| Боковая навигация | посторонняя клавиша могла закрыть панель; `Enter` или `Space` могли вызвать `TypeError` |
| Примеры Apache | отрицательный `Require not host` без положительного provider в `RequireAll` |
| Руководства OpenStack | ссылки на EOL-релиз Newton и устаревшая команда `nova boot` |
| Руководство WordPress | смесь Docker Compose v1 и v2 с устаревшим полем `version` |
| Руководство Lovable | установка Node.js 18 после окончания поддержки |

Целью был не случайный поиск опечаток. Я ограничился областями, которые мог публично обосновать: JavaScript и TypeScript, Shell, инфраструктурные команды, техническая документация и веб-доступность.

## Метод: авторитетный источник важнее интуиции

Для каждого кандидата я проходил один и тот же цикл: находил дефект в текущей ветке, проверял все его копии, изучал официальную документацию соответствующего продукта, искал похожие issues и pull requests, а затем строил измеримый инвариант «до/после».

>Мои правила, не подлежащие обсуждению:
>1. **Никаких PR без конкретного эффекта** — устаревшая команда, сломанное поведение клавиатуры или противоречие официальной спецификации.
>2. **Никаких предположений о продукте** — если для проверки поведения нужен приватный доступ к OVHcloud Manager, я не называю его подтверждённым bug.
>3. **Все затронутые варианты** — если руководство существует на семи языках, я проверяю все семь файлов и их fallback-связи.
>4. **Соразмерная валидация** — тесты и браузер для темы; lint, parsing и точные инварианты для руководств.
{: .prompt-danger }

Такой метод позволяет избежать двух противоположных ловушек: запускать дорогую multi-locale сборку ради простой URL или считать изменение команды правильным только потому, что оно «похоже» на текущий синтаксис.

## Доступность: два дефекта в React-теме

Первый принятый вклад, [PR #473](https://github.com/ovh/ovhcloud-docs/pull/473), заменяет общие wrappers фильтров Pagefind элементами `fieldset`. Изменение занимает два файла: четыре добавления в CSS, затем четыре добавления и шесть удалений в React-компоненте. Целью было не изменить отображение, а дать assistive technologies нативную семантическую группировку.

Проверка объединила Biome, тесты проекта, проверки содержимого и sidebar, вывод всех семи локалей, а затем сравнение вычисленных размеров в браузере до и после. Финальный commit был объединён с сохранением моего исходного commit как родителя merge.

[PR #474](https://github.com/ovh/ovhcloud-docs/pull/474) касался более заметного дефекта. Пять нативных кнопок закрывали sidebar при любом `keyup`. Одновременно с этим пользовательская группа `div[role="button"]` вызывала обработчик мыши, не передавая ему событие. Затем handler пытался выполнить `stopPropagation()` для `undefined`.

Воспроизведение в браузере было детерминированным: до patch `Enter` вызывал `TypeError`, а группа оставалась закрытой. После patch `Enter` открывает её, `Space` закрывает без прокрутки страницы, клавиша вроде `A` больше не закрывает панель, а клик по overlay продолжает работать. Были исправлены семь файлов темы, после чего вклад объединили с сохранением моего авторства.

## Apache: отрицание, которое никого не разрешало

В руководствах по блокировке домена один и тот же пример встречался на семи языках:

```apache
<RequireAll>
  Require not host domain.tld
</RequireAll>
```

Документация Apache 2.4 прямо говорит, что отрицательная директива `Require` сама по себе не может разрешить запрос и что `RequireAll` нужен хотя бы один положительный provider. Поэтому для выражения «разрешить всем, кроме этого домена» не хватало `Require all granted`.

[PR #481](https://github.com/ovh/ovhcloud-docs/pull/481) исправил **14 блоков** в семи файлах. Мой инвариант изменился с 0/14 на 14/14 блоков, содержащих положительный provider непосредственно перед `Require not host`. После одобрения изменение перенесли во [внутренний PR #545](https://github.com/ovh/ovhcloud-docs/pull/545), а затем объединили с trailer `Co-authored-by`, сохранившим моё авторство.

## OpenStack: уйти от Newton и `nova boot`

Два отдельных вклада решали одну фундаментальную проблему: актуальные руководства всё ещё отсылали читателей к историческим инструментам.

[PR #482](https://github.com/ovh/ovhcloud-docs/pull/482) заменил **18 ссылок** на документацию OpenStack Newton 2016 года актуальным руководством OVHcloud по подготовке окружения OpenStack. Старая страница всё ещё рекомендовала Python 2.7, `easy_install` и клиент без поддержки Python 3. В новой используются Python 3, виртуальное окружение и `python-openstackclient`. Исправление было объединено через [PR #515](https://github.com/ovh/ovhcloud-docs/pull/515).

Затем [PR #493](https://github.com/ovh/ovhcloud-docs/pull/493) заменил `nova boot` на `openstack server create` в семи вариантах руководства по запуску скрипта при создании инстанса. Он также исправляет `--key_name` на `--key-name` и неправильно сформированный вариант `--user-data`. Я сравнил синтаксис с текущей документацией OpenStackClient, не утверждая, что действительно создавал инстанс: локально не было ни CLI, ни тестового облака. Patch был объединён через [PR #516](https://github.com/ovh/ovhcloud-docs/pull/516).

## Docker Compose: сделать руководство согласованным

Руководство по WordPress устанавливало Docker Compose 1.29.2 как отдельный бинарный файл, а затем смешивало `docker-compose` и `docker compose`. На чистой машине указанные пакеты не обязательно предоставляли plugin, который требовался командам v2 в том же руководстве.

[PR #483](https://github.com/ovh/ovhcloud-docs/pull/483) перевёл все семь вариантов на пакет `docker-compose-plugin`, удалил отдельную загрузку, унифицировал команды v2 и убрал устаревшее поле Compose `version`.

Я извлёк и распарсил **14 фрагментов YAML**, проверил структуру сервисов `db` и `wordpress`, а затем убедился в отсутствии legacy-бинарника, старого URL и устаревшего поля. Docker на машине валидации не был установлен, поэтому я не выдавал эту работу за runtime-тест контейнеров. Во время review maintainer подтвердил, что patch исправляет сломанную зависимость от Compose v1 и приводит команды в порядок на всех языках, после чего одобрил его.

## Node.js: заменить LTS после окончания поддержки

У [PR #496](https://github.com/ovh/ovhcloud-docs/pull/496) самый маленький diff: по две изменённые строки в каждом из семи языков. Руководство по импорту сайта Lovable использовало скрипт NodeSource `setup_18.x`, хотя поддержка Node.js 18 завершилась 27 марта 2025 года.

Замену на `setup_24.x` я проверил во всех семи файлах и на endpoint NodeSource. Maintainer явно подтвердил пользу обновления: теперь читатели устанавливают поддерживаемую LTS-версию, а не runtime, который больше не получает upstream-исправлений.

## Честная часть: проблема не всегда была в коде

Три вклада не объединили из веток моего fork. Внутренняя система CDS неправильно запускалась для них, поэтому maintainers пересоздали изменения в ветках основного репозитория. Исходные PR #481, #482 и #493 отображаются как закрытые, но заменившие их #545, #515 и #516 действительно объединены.

Это различие важно: закрытый PR не обязательно отклонён, а одобрение ещё не означает merge. Чтобы правильно отследить внешний вклад, нужно пройти по ссылкам на замены до финального commit.

Первый перенос также преподал мне урок об авторстве. Финальный commit #516 не сохранил ни моё исходное авторство, ни trailer `Co-authored-by`. Maintainer объяснила, что убрала trailer из осторожности из-за личного адреса, уже опубликованного в commits, не понимая, что вместе с ним исчезнет и упоминание в GitHub. Переписывать общую историю было бы неразумно. С тех пор я добавляю просьбу о сохранении авторства в каждый PR, который могут перенести; последующие merge сохранили либо мой исходный commit, либо trailer соавтора.

> Технический результат и его авторство — две разные проверки. После merge patch я проверяю финальный commit, а не только badge «Merged» исходного PR.

## Что я вынес из этой работы

Вклад в серьёзную техническую документацию меньше похож на «исправление текста» и больше — на небольшое инженерное расследование. Нужно отличать просто старую страницу от действительно опасной инструкции, стилистическое предпочтение — от противоречия официальной документации, а точечную проверку — от runtime-теста, который ты не выполнял.

Самое полезное здесь — не число PR. Важен метод, который позволяет отказаться от недостаточно доказанной идеи, а затем точно защитить ту, которую отправляешь: upstream-источник, полный охват, инвариант «до/после» и явные ограничения валидации.

Этот первый цикл принят, и продолжение уже состоялось: ещё восемь вкладов приняты в августе (EOL-образы, якоря, маркеры `mdstat`), другие на ревью — подробный итог, и главное, чему меня научили ревью мейнтейнера, — в следующем посте: [«Когда мейнтейнер становится ментором: уроки ревью OVHcloud»](/posts/ru/lecons-des-revues-mainteneur-ovhcloud/). Поэтому вопрос теперь не «сколько PR я могу открыть?», а **«какое улучшение я могу доказать, не прося maintainer поверить мне на слово?»**
